# 2026-08-17 · 终端图像、渲染与参数收口

这一天修的问题跨了三层：模型发来的参数、渲染层的记账、终端图形协议。放在
一起记，是因为它们暴露出同一种失败模式——**报错信息说的原因不是真原因**，
以及同一种解法——**先造出能测的手段，再动手**。

---

## 一、模型传来的畸形参数：从按调用点打补丁改成两个收口

### 现象

一天之内踩到三次，形态各不相同：

| 形态 | 后果 |
|---|---|
| `{"action": "mute", "duration_seconds": ` 半截 JSON | QQ 禁言 → 供应商 HTTP 500 → 回合永久变砖 |
| `"reference_images": "[\"/p.png\"]"` 数组写成字符串 | 参考图静默失效 |
| `"todos": "[{...}]"` 对象数组写成字符串 | todo 工具完全不可用 |
| `"start_line": "1"` 整数写成字符串 | 报「start_line is required」——**参数明明传了** |

最后一种的误导性最强：`as_u64()` 在 `Value::String` 上返回 `None`，和「没传」
是同一个返回值，于是必填校验说它缺失。

### 为什么前两次修都漏了

前两次都在**按调用点打补丁**：

- 补完主循环，漏了子代理（`subagent_runner.rs`）
- 补完落库和历史回放，漏了回合内的活体路径
- 补完字符串数组，漏了对象数组

调用点会增长，补丁跟不上。

### 解法：两个收口

**收口一 · `ChatMessage::assistant`** —— tool_calls 进入消息的唯一入口。在构造
函数里校验参数必须是合法 JSON **对象**。主循环、子代理、历史回放、中断重建
一次全覆盖。

两个刻意的保留：

- **执行侧仍拿原始参数**：`EOF while parsing a value at line 1 column 39` 是给
  模型最有用的反馈——它自己的调用被截断了。
- **落库也保留原样**：`tool_flow` 里那串半截 JSON 是定位根因的唯一取证来源，
  净化掉等于毁掉下次的线索。

**收口二 · `ToolRegistry` 按 schema 还原**。只动工具 schema 自己声明为
array/object/integer/number/boolean 的顶层参数，且只在字符串确实解析成那个
类型时才换。声明成 string 的一个字节都不碰——`run_command.command` 里恰好是
一段 JSON 的情况必须原样透传。布尔收大小写（实测模型发过 Python 风格的
`"False"`）。覆盖 31 个工具的 56 个标量参数、9 个结构化参数。

### 审计

扫了全部 68 处 `as_array()`/`as_object()` 取值点：12 处失败即报错；56 处静默
降级，其中模型供参的已被上面两个收口覆盖，其余全部是在解析第三方 API 响应
（DeepSeek 状态页、AUR RPC、各家搜索 provider、MCP）——那里静默降级是对的，
供应商改了形状不该让工具崩掉。

## 二、query_moegirl「页面不存在」：两个缺陷叠在一起

报告写的是「疑似 API 变更」。不是——三个镜像的 API 实测全部正常。

| 环节 | 实际 |
|---|---|
| 初音未来页面 | **609,690 B** > `MAX_PAGE_BYTES` 512 KB |
| `read_bytes` 超限 | **即报错**，不截断 |
| 落进 fallback | zh 站点的 `action=parse` 被禁用（`Unauthorized API call`）|
| 结果 | 报「page not found」——页面存在，抓取也是 HTTP 200 |

而且 `error_for_status()?` 用的是 `?`，**HTTP 错误码直接外抛、进不了 fallback**。
两个站点的可用性正好互补（zh 的 rest.php 好用而 api.php 被禁，uk 反过来
rest.php 返回 501），于是 `site=uk` 整个不可用。

正文最后本来就要 clip 到 20,000 字符，字节上限只是内存护栏，为它整页失败没
道理——改成截断取前缀。两处都修，新增联网用例覆盖两站。

## 三、终端图片印成满屏：尺寸在进程边界上丢了

### 根因

回合跑在 daemon 里，但 daemon 对 `PrepareForExternalOutput` **一律答 false**，
自己不画图，只把图片资产报上来。真正渲染的是终端这一侧的 `tool.image` 处理。
而那里：

```rust
let size = (name == "show_meme").then(|| configured_meme_size(..)).flatten();
```

**只有 show_meme 算尺寸**，其余一律 `None`，而 `parse_size(None)` 的语义正是
「铺满整个终端」。于是 generate_image、print_image、search_web_images 全部印成
满屏。

daemon 那侧算好的百分比传不过来**也不该传**：`configured_print_size` 依赖
`crossterm::terminal::size()`，daemon 量到的不是用户的终端。

### 解法：尺寸分两段解析

| | 在哪算 | 为什么 |
|---|---|---|
| 百分比默认值 | **CLI** | 只有这一侧知道终端多大 |
| 模型显式要的 `width`/`height` | **daemon 带过来** | 只有它手里有工具参数 |

为此把 `print_size` 拆成 `requested_print_size`（显式值）+ 配置兜底两半，
`ToolProgressEvent::Image` / `AgentEvent::Image` / SSE 载荷都加上 size 字段。
size 刻意不落回放日志——那是这一次的展示偏好，回放时终端可能已经换了尺寸。

顺带修掉一个同类静默忽略：`print_image(width=100)` 在 daemon 模式下此前是无声
丢弃的（daemon 算了，CLI 不看）。

### 实测

| 原图 | 请求框 | 选中网格 | 传输画布 |
|---|---|---|---|
| 1000×1000 | 50×19 | 42×19 = 462×456px | 456×456 |
| 3145×2048 | 50×19 | 50×15 = 550×360px | 550×358 |
| 160×158 | 33×11 | 25×11 = 275×264px | 267×264 |

## 四、LaTeX 非 kitty 路径一律撑到 9 行

块级公式和表格单元格共用 `render_math`，行数由调用方**写死为 9**，而
`halfblock_art` 只约束宽度、垂直方向没有任何上限——终端高度、剩余行数、
配置百分比全都不参与。于是 `E=mc^2` 这种两行就够的式子也被撑到 9 行。

拆出 `render_block_math`：用和 kitty 那条路同一套 retina 语义（RaTeX 以 2x
密度出图，显示尺寸取内容的一半），行数随内容自然分配，`max_rows` 只是天花板。
表格单元格仍走固定行高——那里的固定是对的。

| 公式 | 修前 | 修后 | kitty 路径（独立实测）|
|---|---|---|---|
| `E=mc^2` | 9 | **2** | 2 |
| 黄金比 | 9 | **4** | 4 |
| Attention | 9 | **5** | 5 |

三条全部与 kitty 路径吻合：两条渲染路现在尺寸一致，只差保真度。

### 补：非 kitty 终端改走 chafa

上面只修了行数，公式在 Konsole 这类终端仍是像素块——**同一个终端里图片是
图、公式是像素块**。原因是 `kitty_graphics_supported()` 只认 `xterm-kitty`
和 ghostty，别的一律半块，而半块只有 `▀ ▄ 空格` 三个字形、每格两个垂直采
样，高清 PNG 压进去必然碎。

我起初没做这一步，理由是「公式输出要嵌进 markdown 流里，必须捕获 chafa 的
stdout，而一捕获 chafa 就探测不到终端能力」。**这个前提是错的**：chafa 有
`--probe-mode ctty`，经**控制终端**探测，与 stdout 是不是管道无关。

三个必须配对的细节：

| | |
|---|---|
| `--probe-mode ctty` | 捕获输出也能探测终端能力 |
| `--polite on` | 掐掉隐藏/显示光标的转义，嵌进流里不乱动光标 |
| `-t 0.9` | RaTeX 出的是透明底，阈值放高让背景真正透出去，别被合成成一块底板 |

**行推进随格式而变**，这是最容易漏的一处：

| 格式 | chafa 发出的行推进 |
|---|---|
| kitty | IND×(N-1) + 换行×1 = N ✓ |
| **sixels** | **0** —— 整图一个 blob，一行都不推 |
| iterm | 换行×1 |
| symbols | 换行×N ✓ |

只验了 kitty 格式就以为通用，结果 Konsole（走 sixel）下渲染层以为公式占
1 行、实际占 5 行，后续文字直接写到图上——高的公式压住下一行标题。修法是
把 IND 换成换行、再按实际行数补齐空行，两者都做才与格式无关。

另加一道闸门：**stdout 不是终端就不起 chafa**。管道、重定向、测试都走不到
真终端，chafa 探测不到只会退回符号画，还白付一次进程开销。这道闸门顺带让
三个断言半块输出的老用例原样通过。

至于「同步函数里起进程」的顾虑：`ratex_png` 本来就在同一个函数里做 LaTeX
解析、排版、PNG 编码，都是同量级的同步重活，多一次 chafa 调用不是新的一类
问题。

### 附带：吞掉 RaTeX 的字体噪声

`ratex-unicode-font` 0.1.14 找到字体就无条件 `eprintln!`，没有 env 开关也没
有 feature 门（连读 `RATEX_UNICODE_FONT` 那条分支也照打）。进 REPL 回放带公
式的历史时，屏幕上会冒出两行 `[ratex-unicode-font] found via system-fonts:
…`——daemon 与 CLI 各一次，两个进程共用同一个终端。

字体是 `OnceLock` 缓存、每进程只加载一次，所以趁第一次渲染把 fd 2 临时指向
`/dev/null` 让它把话说完，缓存填上之后再也不会响。重定向 fd 是进程级副作
用，因此只在这一次、且只在这一小段窗口里做。

**这里栽了一次，而且是自己给自己发的假证。** 第一版预热写的是 `parse("x")`
——纯 ASCII。会说话的是 **Unicode 回退字体**，而纯 ASCII 公式压根用不上它，
缓存没填上，真正带中文的公式一来照样打印两行。

更糟的是我"验证"过：跑了个渲染公式的测试，数 stderr 得到 0 行，就宣布修好
了。但**那个测试不加抑制也是 0 行**——它渲染的公式全是纯数学，从来不加载
CJK 字体。这个验证从头到尾没有区分能力。

逐条试出触发条件后才定位准：

| 公式 | 是否加载 CJK 字体 |
|---|---|
| `E=mc^2`、`\int_0^\infty e^{-x^2}dx` | 否 |
| `\text{hello}` | 否 |
| **`\text{中文}`** | **是（打两行，两张缓存各一次）** |
| 裸 `中文`（不在 `\text` 里） | 否 |

预热改用 `\text{中}`，再做真前后对照：**无抑制 2 行 → 有抑制 0 行**。

教训是：**"修完之后现象没了"不等于验证通过——先证明不修的时候现象会出现。**
一个不加修复也是绿的测试，加了修复当然还是绿的，它对这个 bug 毫无判别力。

## 五、回合中途的 token 计量：机制早就有，缺 IPC 那一段

DSH 每完成一步就刷统计，Miyu 的 footer 却要等整轮结束。

机制其实齐了：agent 每完成一次模型请求就发 `RoundUsage`，
`refresh_round_usage` 也写着「回合中途的逐请求刷新」并会立即重绘。缺的是中间
那一段——**回合跑在 daemon 里，而 CLI 两个事件泵的分发表里都没有
`chat.round_usage` 分支**，事件在进程之间掉地上。WebUI 自己解 SSE 所以一直
正常，终端直连模式走进程内事件也正常，唯独日常的「终端连 daemon」中招。

实测（`testkit/dev-smoke/footer_midturn_repro.py`）：

```
修前  43 次 footer 绘制，只有最后 1 次带数字
修后  +4.0s  2.6k/168k(1.5%) · Σ2.6k(C98%)   ← 工具还在跑
      +8.8s  1.9k/1M(0.2%)  · Σ5.2k(C97%)   ← 回合结束
```

第一次还把分支加错了泵（加到后台唤醒那条上），靠插桩才发现日常 REPL 走的是
`try_run_remote_chat`。

## 六、准备提示：批量里的计时每个工具归零

「准备工具 · 1.2s」里的秒数是**计时**不是计数，而 `write_tool_call` 每完成一
个工具就把 `tool_preparing` 清成 `None`，下一个工具进来时重新 `Instant::now()`
——批量调用里秒数来回横跳，反映不出已经等了多久。

拆出一个跨 `write_tool_call` 存活的锚点，整个准备窗口共用一个起点，窗口真正
结束才清（新一轮思考／外部输出／**工具跑完**／回合结束）。「工具跑完」那处
不能少：模型不经思考直接连着发下一批时，没有它秒数会从上一批一路累加。

同时补了两个缺失的提示：`todowrite` →「准备清单」（整张清单都在参数里），
同一条消息里的第 2+ 个工具调用 →「准备工具」（每个单看都不够慢，但参数接连
流完的静默窗口和一次大 patch 一样长）。

## 七、QQ 命令输出没走回复处理插件

`/models` 这类命令的输出此前用 `send_bypass_plugins` 直发，绕过 `before_send`，
所以一长就在群里刷屏，而同样长度的模型回复会被转成图片。命令输出和模型回复
一样是正常产物，没道理两套待遇。

逐个插件核对过 `Command` origin 的落点后改走 `send()`。剩下 6 处 bypass 全部
保留——限流提示、会话解析失败、回合异常兜底。这些恰恰在插件可能不可用、或
插件本身就是问题来源的时候要发出去，多一层依赖就多一次发不出的机会。这条判据
写进了 `send_bypass_plugins` 的文档注释。

## 八、未完成：kitty 图片滚动残影

> **2026-09-07 已解决**，根因与这里的推断不同（图片不是钉在坐标上的整体，
> 而是每帧按占位符行重扫的引用；受限区滚动不搬历史区的引用）。见
> `2026-09-07-kitty图片滚动残影.md`。下文保留当时的记录。

**现象**：打图之后用鼠标滚上去看历史，AI 继续输出把内容顶上去时，图片的底部
切片会一条条向下重复渲染，甚至出现在后续文字的背景里。

**已经用字节级证据排除的**（`script` 全量录像，3.5 MB）：

- Miyu 发的占位符 **2525 个 = 50×15×3 + 25×11，一个不多**
- 全部 **2349 次绝对定位都在 51–57 行**，正文区一次都没碰过
- 4 次图片传输，哈希显示其中两次是同一张（搜图预览 + `print_image` 各一次，
  符合预期），没有重复发送
- 尺寸、图形协议用法、单元格检测、重复渲染路径均已排除

**已定位的机制**（kitty 图形协议规范原文）：

> 设了页边距（DECSTBM）之后，只有**完全落在页内**的图片才跟着滚动；越界的
> 会被**裁剪并留在原地**。

Miyu 的活动区固定在屏幕底部，正文用受限滚动区滚（录像里 1827 次 DECSTBM、
920 次区底定位）。图片是顺着光标往下打的，底部常常正压在活动区上——恰好越界。
此后每一次受限区滚动它都不动，文字走了图不走，一次留一条残影。

**这原本是个死锁**：那个本该把图抬出活动区的滚动，正是 kitty 拒绝对图生效的
滚动。

**试过但不对的修法**：把腾地方的滚动整体改成整屏滚。`apply_output_frame` 在
活动区正常显示时也会走这段，整屏滚会把画着 `┃` 的输入框推进正文——满屏散落
竖线。已退回。

**当前修法**：只在图片刚打完那一刻整屏上滚一次，把它抬进正文页内。那一刻
`suspend()` 已把活动区清空，整屏滚不留痕迹。竖线回归已消除，**但残影仍在**，
说明抬升的量或时机还差一点。

**留下的测具**：

- `testkit/kitty-image/probe.py` —— 单元格像素与占位行数
- `testkit/kitty-image/scroll_probe.py` —— 受限区滚动是否搬图
- `testkit/kitty-image/scroll_variants.py` —— 四种滚动方式对照

## 方法论

这一天最贵的教训不是任何一个 bug，而是**每次都在错误的抽象层上猜**。

1. **报错信息说的原因往往不是真原因**。「start_line is required」——参数传了；
   「page not found」——页面存在且 HTTP 200；「图片太大」——尺寸算对了，是画
   到了预留行之外。三次都是先信了报错，绕了远路。

2. **按调用点打补丁必然漏**。同一类问题一天踩三次，前两次都在补调用点。收口
   要放在类型的构造函数、注册表的分发处这种「唯一入口」上。

3. **没有测量手段就先造测量手段**。footer 那个 bug 是靠插桩定位的——推理指向
   了错误的事件泵，插桩两分钟就指出真凶。图片那个是靠 `script` 全量录像才把
   「Miyu 发错了」和「kitty 画错了」彻底分开。

4. **读规范比猜快**。图片残影猜了四轮，一次搜索找到协议原文，机制立刻清楚。
   应该更早去读。

5. **合成探针要能自证**。中途几个探针因为没清行尾、清屏毁掉证据、滚动量太小
   而给出误导结论，浪费了好几轮往返。探针必须先能证明「它自己做的事生效了」。
