# 2026-09-04 · agy 中转的全量重放被静默截断

> **状态：OPEN — 已定位根因，未修复。** 现象在写这份报告时仍在持续发生
> （最近一次复现：09-04 18:33 JST，见 7.2）。修复合入并通过验收后，请连同
> 验收记录一起移入 `docs/fixed/`。

这份报告记两个**独立**的缺陷。它们叠在一起才产生了用户可见的现象，但根因、
修复位置、紧急程度都不一样，复核时请分开看。

- **缺陷 A（正确性）**：续传链断掉后的「全量重放」载荷超过 `agy` 对单条 user
  输入的 **192,000 字节**硬上限，`agy` 从**尾部**截断——而本轮真实消息恰好排在
  载荷末尾——然后返回 SUCCESS。Miyu 全程无感，模型去回答截断处悬着的旧残片。
- **缺陷 B（效率 + 未定位）**：那些全量重放里约 80% 本不该发生。今天 15 次危险
  重放只有 3 次有正当理由，其余 12 次原因未明。它们吃掉了当天送进 agy 的
  **92%** 字节，并让前缀缓存全程失效。


## 三、缺陷 A：全量重放载荷被 agy 从尾部截断

### 3.1 决定性证据

seq 213 对应 agy 会话 `05b96b52-2fd2-4618-8e4d-594f5a889402`，它的第 0 条
USER_INPUT（`transcript_full.jsonl`，未截断记录）：

- 长度 **146,452 字符 / 192,000 字节**
- 结尾是 `<truncated 201988 bytes>`
- 再之后是 agy 自己追加的一句：
  `NOTE: The output was truncated because it was too long. Use a more targeted
  query or a smaller range to get the information you need.`

模型紧接着那一步的 thinking（原文）：

> **Assessing Prompt Truncation** — The prompt ends abruptly with a truncation
> marker. This raises the critical question of whether the prompt itself is cut
> off… Examining the end of the prompt confirms the truncated state.
> **Processing apology message.** — The user's apology needs a concise and
> appropriate response within the given constraints.

模型明说自己看到的是被截断的输入，并且在残片里找到了一段「道歉」去回应。而
Phaethon 的 grub 问题在被丢掉的那 201,988 字节里。

被保留的那截尾巴停在一段**旧回合**的中间（发送者紫藤 QQ:3563504929，
msg=1532585531，还挂着那一轮的 `<qq-inflight>` 与
`[SystemInfo:LongReplyImageConversion]`），`</conversation-history>` 都没闭合。
模型看到的「最后一条用户消息」就是这段悬空残片。

### 3.2 是谁截断的

**是 `agy`。** 三条依据：

1. `<truncated %d bytes>` 与那句 NOTE 都是 `/usr/bin/agy` 里的字符串常量；Miyu
   源码全库 grep 不到（`grep -rn "was truncated because it was too long" src/`
   为空）。
2. 二进制里带着干这事的 Go 包路径：
   `google3/third_party/jetski/cortex/core/tooldecorators.(*outputTruncationTool)`
   与 `.../gemini_coder/framework/core/serializers/truncation`。
3. **逻辑上排他**：agy 报出的是精确数字 `<truncated 201988 bytes>`，说明
   393,988 字节它整段收到了，是收到之后自己决定只留 192,000。所以不可能是
   stdin 管道截断，也不可能是上游 API 拒收。

顺带一个值得记的细节：干这事的是 agy 的**工具输出**截断器
（`outputTruncationTool`），那句 "Use a more targeted query or a smaller range"
本来是写给工具结果看的。agy 把 user 输入也塞进了同一条截断流水线。这是 agy 的
毛病，但不改变 Miyu 不该一次甩 40 万字节的事实。

### 3.3 上限实测：192,000 字节

抽五次全量重放，量「保留部分的 UTF-8 字节数」：

| conv | kept_chars | **kept_bytes** | dropped_bytes | total |
|---|---|---|---|---|
| fd400f69 | 143,028 | **192,001** | 2,275 | 194,276 |
| 0b07647a | 143,028 | **192,001** | 93,960 | 285,961 |
| 319af2f5 | 143,028 | **192,001** | 162,239 | 354,240 |
| 05b96b52 | 146,293 | **192,000** | 201,988 | 393,988 |
| da98b3a0 | 146,293 | **192,000** | 227,714 | 419,714 |

字符数随内容波动，字节数钉死在 192,000。**上限是字节，不是字符，不是 token。**

### 3.4 为什么砍掉的正好是本轮消息

`src/llm/openai_compatible/cli_relay/payload.rs:63` `render_user_blocks()` 的排布：

```
blocks[0]  = <conversation-history> 整段历史转写      ← 全量重放时才有，巨大
blocks[1..] = 活跃尾巴：本轮 user 消息、<runtime>、
              <persona-reminder>、<qq-request-context>、
              <context-images>、<associative-memory> …   ← 本轮真正要回答的东西
```

`src/llm/openai_compatible/antigravity/mod.rs:365` 把这些块直接拼进 stdin。agy 拼
成单条输入后从**尾部**截断，于是先死的永远是活跃尾巴。**函数里没有任何体积
上限。** 三条 CLI 中转线（claude-code / antigravity / codex）共用这份渲染，所以
另外两条同样暴露，只是各家上限不同、目前没有实测数据。

### 3.5 相关性：100%

把当天每次全量重放的原始体积和它产出的第一条回复对齐：

| 原始体积 | 是否被砍 | 回复 |
|---|---|---|
| 115,310 / 117,742 / 120,967 / 131,877 / 134,149 | 否 | **全部正常** |
| 198,979 / 227,371 / 274,506 / 289,798 / 393,988 / 405,435 / 410,950 / 419,714 | 是 | **全部答非所问** |

没有例外。同一条 agy 会话里，第 0 条（全量重放，被砍）产出垃圾，之后的增量
（1.6KB / 1.8KB，没被砍）产出正确答案——`0f19d172` 就是现成的对照组。

### 3.6 为什么历史常年超线：两个预算，两种单位，没人对过账

| | 数值 | 单位 |
|---|---|---|
| agy 单条 user 输入上限 | 192,000 | **字节** |
| Miyu 给这个会话的上下文预算 | 168,000 × 0.9 = 151,200 | **token** |

`168000` 来自 `context.default_context_window`
（`~/.miyu/config/config.jsonc:405`）。`gemini-3.8-flash-high` 既不在 antigravity
provider 的 `model_context_window` 里，也不在 `models_cache.json` 里，所以走
`src/config/provider_ops.rs:683` 的第三级兜底，`ContextWindowSource::Assumed`
——这个数跟这个模型没有任何关系。

15 万 token 的中英混排群聊折成字节约 **40 万**，是传输上限的两倍多。所以只要
发生全量重放，且不在刚 pop 完的窗口内，**必然超线**。

### 3.7 pop 为什么救不了

QQ 群这一档单独配了淘汰策略（`config.jsonc:737`）：

```jsonc
"group_context": { "on_overflow": "pop", "trim_batch_ratio": 0.6 }
```

pop 确实在工作：这个会话现存 59 轮（seq 167–225，`hidden` 全为 0），seq 1–166
已被淘汰。全量重放体积的时间序列里能直接看到锯齿（第七节）。

但落点是按 token 算的（168,000 × 0.4 = 67,200 token），折成字节在
**11.5 万 ~ 19.9 万之间浮动**——`04:09` 那次 pop 后的落点就是 **198,979 字节，
已经越线**。也就是说连「刚 pop 完」这个本该最安全的时刻都开始不安全了，而且
随群里中文/图片比例变化只会更糟。

调 `trim_batch_ratio` 不是解法：那是拿 Miyu 的记忆长度去赌一个换算关系，换个
CLI、换个语种就又骑回线上。

### 3.8 还有一条自救路径是废的

`src/agent/turn_loop/mod.rs:255` 有一条 overflow 自救：供应商回报上下文溢出错误
时就地压缩再重试。**这条在 antigravity 线永远不会触发**——agy 不报溢出错误，
它闷声截断然后返回 SUCCESS。「撑爆了就压缩」这个兜底收不到信号。

## 四、缺陷 B：本不该发生的全量重放

### 4.1 术语

**全量重放** = 不带 resume id 启动 `agy`，它开一条**全新的** conversation，Miyu
把当前可见历史整个塞进一个 `<conversation-history>` 块作为第一条 user 输入。
今天 24 次全量重放 = 24 个新建的 `brain/<uuid>/` 目录，一一对应。历史**从不**
往老会话里重发。

另有一种形态别混淆：续传命中了**更老**的前缀时，增量里会带一个几 KB 的
`<conversation-history>` 补块，补的是那条 agy 会话还没见过的几条消息。不是重复，
也不撞上限。今天 130 条增量里有 18 条是这种（见 4.4）。

### 4.2 代价

09-04 送进 agy 的字节：

```
全量重放   24 次    6,406,344 字节    平均 266,931
增量      130 次      552,443 字节    平均   4,249
→ 16% 的请求吃掉 92% 的载荷
```

且这些请求的 `cache_read` 基本全是 0——每次新会话意味着前缀缓存从头开始。

### 4.3 续传是怎么判定的

`src/llm/openai_compatible/cli_relay/session.rs`：

- 键是**逐消息哈希链**，种子掺 provider / model / system prompt。
- 映射表是 `static SESSIONS: Mutex<Vec<SessionEntry>>`（`session.rs:41`），**纯
  进程内存**。模块头原话："匹配不上就重开会话全量重放——只损失效率，不损失
  正确性，**因此状态不做持久化**"。
- `ResumePlan::record()` 登记的是**预测**而非观测：`conversation.len() + 1`，多出
  的那一条是 `ChatMessage::assistant(本轮正文, None)`。

**注意：那句「只损失效率，不损失正确性」现在是错的。** 缺陷 A 让全量重放变成
了「丢掉本轮问题」。这是本案里最值得记住的一条——一个正确的兜底假设，被下游
一个它不知道的硬上限废掉了。

三份状态里两份落盘，中间那根线不落盘：

| | 在哪 | 落盘 |
|---|---|---|
| Miyu 的对话历史 | `conversation.db` | ✅ |
| agy 的对话内容 | `~/.gemini/antigravity-cli/conversations/`（此刻 122 条） | ✅ |
| **前缀 ↔ agy 会话 id ↔ 已覆盖条数** | `session.rs:41` 的 static | ❌ |

### 4.6 已排除的假设（别重走）

以下都查过并排除，附依据：

| 假设 | 结论 | 依据 |
|---|---|---|
| moderation 预检注入把模型带成群管口吻 | 排除 | `<qq-moderation-precheck>`（`inject.rs:834`）只在 `judged.moderation.violation` 时注入；seq 213 决策日志无 violation |
| 好感度/情绪/群管记录被整块注入提示词 | 排除 | 好感度快照 v7 起已不进提示词（`inject.rs:841` 注释）；`qq_group_management` 的 30KB `offender_history` / 32KB `management_events` 只经工具查询暴露 |
| 工具面档位切换（admin ↔ 非 admin 各续各的会话） | 排除 | 04:00–08:38 全部 59 轮 `is_admin` 皆为 false，未发生切档 |
| 带工具的回合化石成多条消息，撑破 `record()` 的 +1 预测 | 排除 | 中转侧工具活动折成一条 `remote: true` 轮（`turn_loop/mod.rs:1121`），`replay_rounds()` 明确 `.filter(!round.remote)`（`tool_report.rs:347`），根本不进历史回放 |
| 某轮失败没登记导致断链 | 排除 | 即使某轮未登记，更老的条目仍在表中且仍能命中，只会多一个 catch-up 补块，不会退化成全量重放 |
| `SESSION_CAP = 64` 整表清空 | 本时段排除 | 当天全天仅新建 25 条 agy 会话；08:14 重启后表为空，远够不到 64。（作为长时段的诱因**未排除**：每次全量重放 +1 条永不回收的条目） |
| 供应商在故障窗口返回陈旧补全（`repeat_gate.rs` 模块头记载的 08-24 现象） | 排除 | 本案的错误输出与截断状态 100% 相关；未截断的请求全部正常 |

### 4.7 结构上还剩什么

要让 `find_resumable` 一条都命不中，只可能是：映射被整体清掉（进程重启 /
`SESSION_CAP` 清空），或链种子/前缀字节变了（system prompt 变更 / 历史被改写）。

一个**未证实**的可疑信号：`~/.miyu/state/prompt-fingerprints/` 只在系统提示词
指纹变化时写文件，其中两个文件的 mtime 正好是 **16:53:11 和 17:00:31**（= seq
213 与 seq 219 的时刻），写入的是同一个新指纹。但尚未确认这两个文件属于哪个
会话（文件名是 `blake3(session)`，环境里没有 b3sum），**不能作为结论**。

## 五、放大器

1. **自我强化**：被截断的坏回复会作为 `[you]` 的发言进入群消息记录，在之后每
   一轮的 `[Prior group chat records]` 里重放，成为模型的 few-shot 样例。所以
   09-04 04:09 之后切口稳定落在中午那场禁言风波附近，输出就固化成同一句训话。
2. **重试覆盖正确答案**：见 4.5。
3. **模型自己在圆场**：seq 214 与 221 都自发解释「刚才回别人消息串台了不是说
   你」——群友看到的是一个会为自己的错乱找借口的 bot。

## 六、修复方案

### B′（先做，最便宜，零行为变更）

1. `find_resumable` 返回 `None` 时打一行带原因的 warn：表内有无该会话条目 /
   种子是否相符 / 哪一位前缀失配。
2. 渲染完载荷、送进子进程之前量一次字节数，超过本线上限就打 warn 并记进
   `cache-usage`。

目的：把 4.4 里那 12 次未知在半天内定死。**不加这行日志就动 C，等于继续猜。**

### A（止血，必做）

### 9.2 缺陷 B 的「12 次未知」已定位——不是一个原因，是三个机制叠加

**机制 1：带图片的回合必然断链（主因，覆盖全天大多数全量重放）。**

- 活体：`src/agent/input.rs` 里当前模型吃图时，用户消息构造成

  `Parts` 与 `Text` 字节不同 ⇒ 链在这一轮断掉 ⇒ 之后**所有**登记过的前缀都
  匹配不上 ⇒ 全量重放。
