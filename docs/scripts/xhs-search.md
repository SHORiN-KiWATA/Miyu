# xhs-search —— 给 AI 用的小红书检索工具

一个单文件脚本，形态对齐 `~/Documents/github/Miyu/src/scripts/goofish-search`：
可以直接当命令行用，也可以作为 Miyu script 工具给 AI 调（stdin JSON → stdout JSON）。
只依赖系统 `python3` + playwright + 一个 Chromium 系浏览器。

## 可行性结论（2026-08-29 实测）

| 问题 | 实测结果 |
|---|---|
| 有官方检索 API 吗 | 没有。只有创作者/广告主侧接口，拿不到全站搜索 |
| 匿名能搜吗 | **不能**。游客会话（`guest:true`）调搜索返回 `-104 您当前登录的账号没有权限访问`；连游客态都没有时是 `-101 无登录信息` |
| 签名能自己算吗 | 页面里 `window._webmsxyw(uri, data)` 还在，能签出 `X-s`/`X-t`。**但不够** —— 还要 `x-s-common`，它会话内不断变化（一次页面加载里就出现 5 个不同取值），复用旧值无效 |
| 手搓请求的代价 | 头凑不齐 → `300011 当前账号存在异常`，**并且会把登录态直接搞掉**。踩过一次，别再试 |
| 所以方案是 | 打开真实页面，让站点用它自己的签名发请求，我们只截 JSON 响应 |

搭的过程里踩到的几个坑（都在代码注释里标了）：

| 坑 | 真相 |
|---|---|
| `goto(wait_until="domcontentloaded")` 必定 60 秒超时 | 登录态下这些页面有长期挂起的子资源，DOM 事件迟迟不触发，但内容其实早渲染好了。用 `commit` |
| 笔记正文接口抓不到 | 正文根本不走接口，SSR 在 `window.__INITIAL_STATE__.note.noteDetailMap` 里；评论也在同一个 store，滚动时自己增长 |
| 排序筛选点了没反应 | 面板是 **hover** 展开的，而且鼠标一离开「筛选」就收起 —— `click()` 要移动鼠标，移到一半面板就没了。只能直接派发 DOM click |
| 切了排序结果却没变 | 切换前抓到的是旧排序的结果，混在一起了。必须在"点击那一刻"清空已收集的批次 |
| **跑一次挂住之后，之后每次都挂死，Ctrl+C 还杀不掉** | 上次运行被中断时 Python 死了、它拉起的 Chrome 活了下来占着 profile。flock 只协调我们自己的进程，拦不住这个孤儿。现在拿到 flock 后先按 `/proc` 扫出并杀掉孤儿（那时按定义不存在其它合法实例），Singleton 锁一并清 |
| Ctrl+C 按了没反应 | sync Playwright 阻塞在驱动管道上会把 KeyboardInterrupt 吞掉。改成信号处理器里清掉 chrome 再 `os._exit`，实测 1.1 秒退出、无残留 |

一句话：**能做，但必须挂一个登录账号，而且只能"借站点自己的手"发请求。**

对比两种常见做法：

- **纯逆向签名**（如 Spider_XHS）：快、不用浏览器，但要一直跟版 `x-s` / `x-s-common`，且失败代价是掉登录态。
- **DOM 抓页面**（如各种 Playwright MCP）：稳，但要等渲染、解析 DOM，慢且字段脏。
- **本项目**：浏览器负责导航和签名，数据仍来自官方 JSON 接口。不跟版算法，字段还是干净的。

## 用

```bash
cd ~/Projects/xhs-search
./xhs-search                             # 不带参数 → 打印帮助
./xhs-search login                       # 扫码登录，终端直接出二维码，只需一次
./xhs-search "手冲咖啡"                   # 关键词 → 搜索
./xhs-search "<笔记链接>"                 # 链接 → 看正文
./xhs-search "<笔记链接>" --comments 20   # 正文 + 20 条评论
./xhs-search "拿铁" --sort 最多点赞 --type 图文 --limit 30 --json
```

命令只有两种形态：**给关键词就是搜，给链接就是读**。`search` / `note` 子命令还在，
但不用手写 —— 参数长得像链接或 24 位 note_id 就去读正文，否则当关键词搜。

Miyu script 工具（stdin JSON）：

```bash
echo '{"query":"手冲咖啡","limit":10}' | ./xhs-search      # 关键词 → 搜索
echo '{"query":"<笔记链接>","limit":20}' | ./xhs-search    # 链接 → 正文 + 20 条评论
echo '{"action":"status"}' | ./xhs-search
```

`action` 不用传，按 `query` 的内容自动判断 —— 模型少一个字段要想。

**已装进 Miyu**（2026-08-29）：安装副本在 `~/.miyu/data/scripts/xhs-search`，
注册 id `xhs_search`，归入 `research` / `shopping` 组，超时 300 秒。
schema 里刻意**不设 `required`** —— `action=status` 不需要 `query`，
硬性 required 会把这个动作彻底堵死；漏传时脚本自己会报清晰的错。
改完源码记得重新 `cp` 一份过去，两边不会自动同步。

## 设计上的几个选择

- **搜索结果不含正文**。一次 20 条正文能塞爆上下文。让模型先看标题挑，再对少数几条取正文。
- **`xsec_token` 拼进返回的 url**。2024 年后笔记详情/评论必须带它且与来源绑定，
  裸 `note_id` 多半取不到。下游工具原样传 url 就行。
- **排序/类型靠点 UI**。这些参数在请求体里，我们不构造请求所以改不动。
  类型走顶部标签，排序走 hover 出来的筛选面板；点不动就退回综合排序，
  不让整次搜索失败。降级时返回结构里 `degraded=true`，`sort`/`type` 写的是
  **实际生效值**、`sort_requested` 才是你要的那个 —— 只写日志不行，
  AI 调用时日志是静默的，会把综合排序的结果当成"点赞最多"。
- **评论连楼中楼一起给**。小红书的问答几乎全在楼中楼：主楼是"求名字/多少钱"，
  博主的回答在 `subComments` 里。只取主楼等于把一堆没有答案的提问交出去。
  `limit` 只管主楼条数，回复不占额度。
- **登录态在 `~/.cache/xhs-search/profile`**（`XHS_PROFILE_DIR` 可覆盖）。
  用持久化 profile 而不是导出 cookie 字符串 —— `a1` 这些字段会自己续期，
  导出的 cookie 反而容易过期。
- **profile 文件锁**。两个进程同时开同一个持久化 profile 会撞出难懂的报错，
  所以在这里先排队（`XHS_LOCK_WAIT`，默认 120 秒）。
- **二维码直接画在终端里**。系统 Python 装不了 `qrcode`（externally-managed），
  又不想为此塞一个 QR 编码器进来，所以让浏览器把页面上那个二维码读成 0/1 矩阵
  （它本来就有完整图形栈），Python 只负责用半块字符 + 真彩背景画出来。
  显式指定前景/背景色，免得终端主题把黑白反过来导致扫不出。
- **出错返回 `{error, fix}`**，让模型把 fix 念给用户，用户自己处理。
- **绝不无限期挂住**：看门狗默认 180 秒（`XHS_DEADLINE`，`login` 时自动关闭），
  等 profile 锁时也会立刻在 stderr 说明自己在等谁，不装死。

## 返回结构里必须看的几个字段

给 AI 用的工具，最怕的不是报错，是**结果打了折扣但长得跟正常的一模一样**。
所以这几个字段跟数据本身一样重要：

| 字段 | 出现在 | 含义 |
|---|---|---|
| `warnings` | 都有 | 有内容就说明结果有折扣，逐条读 |
| `degraded` | search | 筛选/排序没点动，退回了综合排序 |
| `truncated` | search | 抓到一半被限频，返回的是残缺结果，不代表"就这么多" |
| `comments_returned` / `replies_returned` | note | 实际给了几条主楼、几条回复 |
| `comments_has_more` | note | false = 已经翻到底，加大 limit 也没用 |
| `replies_truncated` | 每条评论 | 该楼的回复没展开完（站点要点"展开更多回复"） |

`comments_count` 是**站点口径、含楼中楼**，跟 `comments_returned` 对不上是正常的，
不是抓漏了 —— 一条"18 条评论"的笔记很可能只有 3 条主楼，另外 15 条都在楼中楼里。

## 风险与边界

- **出口 IP 在日本**，小红书对境外 IP 的风控明显更严（实测 `access_check` 直接
  `reason: "ip"`）。这是这台机器上最大的不确定性来源。
- **要一个真实账号**，建议用小号。自动化访问被判异常的代价落在这个账号上：限频、
  掉登录态，极端情况封号。已经实测掉过一次登录态。
- **搜索有账号级日频上限**，刷太猛会返回"今日搜索次数已达上限"，换 IP 没用。
  正因为每次搜索都在烧这个额度，参数名和 `sort`/`type` 的值拼错时脚本会**直接报错退出**，
  不会默默用默认值跑完 —— 白烧一次配额还得出错结论，比报错难受得多。
  这个校验发生在开浏览器之前，报错不花配额。
- **同账号别多个网页端同时登录**，会互相踢下线。
- **只读**。刻意不做发布/点赞/评论 —— 写操作的封号风险和这个工具的价值不成正比。
- 抓的是公开可见内容，个人调研用；别批量采集、商用或再分发。
