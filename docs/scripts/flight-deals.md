# flight-deals —— 查机票价格，顺带找出哪天走最便宜

单文件脚本，**零依赖**（只用 Python 标准库），`./flight-deals` 直接跑。
给出发地、目的地和日期，把行程按价格拉回来排序；日期没定死时扫一个窗口，
直接告诉你哪天走哪天回最划算。

## 可行性结论（2026-09-01 实测）

| 事情 | 结论 |
|---|---|
| Google 航班纯 HTTP 抓取 | ✅ 一条 GET 就出结果，不用浏览器。单次 ~1 秒，40~130 条 |
| 往返总价 | ⚠️ Google 的往返模式确实直接给总价，但返程班次抓不到、价格只是下限 —— 实测后改成两次单程相加，见下面「只查单程」一节 |
| 舱位 / 人数 / 直飞筛选 | ✅ 全部生效，实测经济 ¥2,072 < 超经 ¥4,514 < 商务 ¥4,998 < 头等 ¥34,822 |
| 并发扫日期 | ✅ 16 个组合 6 并发 4.5 秒跑完，未触发限流 |
| 航班号 / 机型 | ✅ 不在 aria-label 上，但在首屏的 `AF_initDataCallback` 数据块里，实测覆盖 87~100%（对不上号的行宁可留空） |
| 碳排放 | ⚠️ 数据在页面上，但在另一个 `aria-label` 里，跟行程的对应关系只能靠 DOM 顺序猜，宁可不要 |

### 关键发现一：`tfs` 参数可以自己拼

`google.com/travel/flights` 的航线/日期/舱位/人数编码在一个叫 `tfs` 的参数里，
base64url 过的 protobuf。这是零依赖的前提 —— 拼得出 `tfs` 就不用开浏览器。

```
3 { 2:<yyyy-mm-dd>  5:<最大经停数>  13{2:<出发机场码>}… 14{2:<到达机场码>}… }
  每程一段；往返给两段(去程 + 回程)，顺序即行程顺序
9:<舱位 1经济 2超经 3商务 4头等>
8:1 每位乘客一个（1=成人 2=儿童）
19:<1往返 2单程>
```

一程里 13/14 可以给多个机场码，于是「上海」= `PVG+SHA`、「东京」= `NRT+HND`
可以一次查完，不用分开查再合并。

**最容易踩的坑：机场码在 `Airport` 消息的 field 2，不是 field 1。**
写成 field 1 时 Google 不报错，而是静默退化成一张促销落地页 —— HTTP 200、
页面正常、解析出 0 条。开发时在这上面卡了一轮。

### 关键发现二：零结果有三种，必须分开

Google 在**这条航线这个日期一班都连不上**时，和在 **`tfs` 拼错**时，
返回的页面长得一样：HTTP 200、没有结果列表。脚本靠结果页上的排序控件
（`aria-label="Sorted by …"`）当标记，把三种情况分开：

| 情况 | 有排序控件 | 有价格卡片 | 脚本行为 |
|---|---|---|---|
| 正常 | ✅ | ✅ | 出结果 |
| 这天真没航班 | ✅ | ❌ | 返回空列表，上层报「没有可售航班」 |
| tfs 没被接受 / 偶发限流 | ❌ | ❌ | 退避重试 3 次，仍失败才报错 |

重试次数正好把最后一格里的两种分开：`tfs` 拼错是确定性的，重试必然同样失败；
偶发限流重试就好。**没有这层重试时，并发扫窗口会偶发失败，并被误诊成
「机场码不存在」，把人引到完全错误的排查方向上** —— 实测 12 个组合里错报 2 个。

### 关键发现三：航班号在数据块里，不在 aria-label 上

一开始只 grep 了 `aria-label` 就下结论说「航班号得点开详情才加载」，**这是错的**。
整份航段明细（航班号、机型、每段的起降机场和时刻）就嵌在首屏的
`AF_initDataCallback` 数据里：

```
["9C",["Spring"],[[… "PVG","Shanghai Pudong…","Narita…","NRT",
                   [15],null,[18,40],160, … "Airbus A320", …,
                   ["9C","6217",null,"Spring"] …]]]
```

那份数据是一大坨靠下标定位的数组，没有任何自解释的字段名，逐层写死下标很脆。
所以这里**按形状认航段**（第 3/6 位是三字码、第 4/5 位是机场全名），
Google 挪动别的字段不影响。

这条链路刻意只做**锦上添花**：抽不到就没有航班号，aria-label 那条主链路照常
出结果，表里那一列直接不出现（而不是留一列破折号）。反过来做——拿数据块当主源
——风险大得多。`doctor` 会盯着覆盖率，低于 80% 报红。

### 关键发现三点五：对号的键必须够唯一，撞上了宁可不印

两边对号入座的键，一开始用的是 `(出发机场, 起飞时刻, 到达时刻)`，**不够唯一**。
实测北京→洛杉矶单日 61 个键里撞了 6 个：一堆华南出发的行程绕不同城市飞广州、
再接同一班 CZ327 跨洋，起降机场和时刻一模一样。撞上时先到先得，结果是把**别人的
航班号贴到这一行上**——`2 转` 的行印出两个号，首段还是错的。印错的号比不印危险
得多，人真会照着去买票。

现在的键是 `(出发机场, 到达机场, 起飞时刻, 到达时刻, 段数)`，值是一串**候选**
而不是一个：

- 加**到达机场**，同城多机场查询（东京→上海 PVG/SHA）的撞车清零；
- 加**段数**，北京→洛杉矶从 6 降到 5；
- 还剩的用 **aria-label 那边的中转地名**再筛一道（`Guangzhou` ⊂
  `Guangzhou Baiyun International Airport`，双向子串），6 组全部消歧成功；
- 筛不出唯一的就整行印 `—`。北京→洛杉矶 60 行里剩 4 行留空，换来印出来的一定对。

试过拿**中转时长**当第六维（数据块里段的日期+时刻能算出来），覆盖率从 85% 掉到
24%——aria-label 那边的时长跟算出来的对不上，此路不通。

### 关键发现四：中转有两种句式

```
…layover at Shanghai Pudong International Airport in Shanghai.
…layover in Taipei City. Transfer here from Taiwan Taoyuan to Taipei Songshan.
```

后一种是**中转要换机场**（得跨城跑一趟），对行程可行性影响极大。
只写 `at` 那版正则的话，换机场的中转会静默变成一个空白的中转格。

### 关键发现五：不认识的币种不会报错，会静默回退成美元

`--currency RMB` 不报错，也不是没生效 —— Google 直接按 `gl` 回退（`gl=us` 就是
美元）照常出价，脚本又拿用户写的字符串当前缀原样印：

```
| 1 | RMB 78 | GK211 | Jetstar | 1h50m |     ← 同一班，--currency CNY 是 ¥523
```

`78` 看着像捡了个大漏，其实是 78 美元。`RMB` 恰恰是人民币最常见的民间写法。

真值一直就在手边：`_L_PRICE` 的第二个捕获组抓的正是 `US dollars` / `Chinese
yuan`，以前解析完直接扔了。现在拿它跟请求的币种对一次，不一致就硬停 ——
数字照出、单位是别人的，比报错危险得多。

`CURRENCY_NAMES` 只收录常用的十种，**表外的币种不能一概判错**（Google 支持一百
多种），只有「回退成美元」才是没被接受的确凿信号。

## 用法

地名写中文、英文或 IATA 三字码都行。写城市名会把同城机场一起查
（上海 = PVG+SHA，东京 = NRT+HND），写三字码就只查那一个。

```bash
flight-deals -f 上海 -t 东京 -d 2026-10-01                 # 单程
flight-deals -f 上海 -t 东京 -d 10-05 -r 10-10             # 往返，开头给合计
flight-deals -f 上海 -t 东京 -d +30 --nonstop --seat all   # 只看直飞，四舱位比价

# 日期没定死 —— 这才是主打功能
flight-deals sweep -f 上海 -t 东京 -w 09-29..10-08 --days 5-7

flight-deals trend -f 上海 -t 东京   # 这条航线底价涨还是跌（要先攒几天）
flight-deals trend                   # 历史库里有哪些航线
flight-deals airports 东京           # 东京有哪些机场、三字码是什么
flight-deals doctor                  # 环境自检

flight-deals -f PVG -t NRT -d +30    # 三字码：只查浦东→成田
flight-deals airports 东京           # 不确定三字码就先查一下
```

`sweep` 刻意**不做**「出发日 × 返程日」的笛卡尔积 —— 那里面绝大多数组合
（当天往返、玩二十天）没人会考虑，白白多花几十次请求。真实请求是
「国庆这几天里去玩五到七天」，所以按「窗口内滑动一段固定时长」枚举，
组合数从平方降到线性。返程日必须也落在窗口内（窗口 = 这段时间我能出门）。

## 设计上的几个硬规矩

**出发地和目的地必须显式给出，脚本不猜。** 猜错了输出看起来完全正常，
比直接报错危险得多。地名解析也只做精确匹配，匹配不上就报错并给候选 ——
hotel-deals 里搜「苏州金鸡湖」返回 30 公里外昆山的酒店、价格是真的、
排版正常、没有任何报错，机票同理（「宁波」模糊到「南宁」谁也看不出来）。

**内置机场表只求准不求全。** 硬凑数量必然掺进记错的码，而错码的后果是
「查了另一座城市的票，输出完全正常」。表里没有的地方，用户直接写三字码
就能用（passthrough），所以覆盖率不足最多是多打三个字母。

全表 2026-09-01 逐条对着 Google 实测过一遍，揪出两个**已退役**的码：

| 原码 | 现况 | 正确的码 |
|---|---|---|
| `PNH` 金边 | 德崇新机场启用后停用，Google 完全不认 | `KTI` |
| `REP` 暹粒 | 吴哥新机场启用后关闭 | `SAI` |

机场改码是这张表最主要的腐烂来源，隔一阵子值得重跑一次校验。

**结果全部列出，不做任何合并；靠筛选控制信息量。** 手机订票 app 都是这么做的
（携程、Skyscanner 都列全 + 筛选面板），一度做过「同价同航司折叠成一条」，
被否掉了 —— 折叠要么记号会误读（`21:45 +6` 撞上航班表里 +N = 次日到达的行业
写法），要么键太松把真正不同的中转地也藏掉，而它想解决的问题其实是筛选的活。

同价同航司的重复率实测很高（上海→东京 40%、北京→大阪 53%、上海→伦敦 67%，
南航一个价能有 32 班），所以筛选维度要够用：

| 维度 | 参数 | 说明 |
|---|---|---|
| 航司 | `--airline 南航 春秋` | 中英文都认，匹配到词边界（ANA 不会命中 Asiana） |
| 起飞时间段 | `--depart-time 08:00-18:00` | 对付「同价二十班只差几点走」最有效的一个；`24` 和 `24:00` 都是 23:59 |
| 直飞/经停 | `--nonstop` / `--max-stops 1` | 经停数交给 Google 过滤 |
| 排序 | `--sort price\|duration\|depart\|arrive\|stops` | 默认 price |
| 条数 | `--top 30` | 没显示的条数会在输出里说明，不静默截断 |

输出里的 **各航司最低价** 和 **各舱位最低价** 两栏，作用相当于 app 的筛选面板：
先看有哪些航司、各自最低多少钱、有几班，再决定筛谁。

**舱位可以一次比几个。** `--seat business`、`--seat economy business`、
`--seat all` 都行；每多一个舱位多一次并发请求（四个舱位实测 1.4 秒），
结果并进同一张表按价排，多出一列「舱位」。实测上海→东京：
经济 ¥983 / 超经 ¥2,532 / 商务 ¥3,987 / 头等 ¥20,369。

**一个舱位没票不该拖垮其他舱位。** `--seat all` 是四个并发请求，济州这种线根本
没有头等舱，那一路会抛 `Failed`；异常从 `pool.map` 的迭代甩出来，经济舱查到的
十几条就一起陪葬了。现在每路的异常收进返回值，全挂了才报错，挂一路就在「注意」
里写明哪个舱位没查到 —— 偶发限流同理。

**汇总数字一律显式算，不许拿排序后的第一项。** 这个坑在这份脚本里踩过三次：
汇总行的「最低价」、各舱位的「班次数」、sweep 的「最快」列，写法都是默认列表按
价格排好了。按价排序时恰好正确，换 `--sort duration` 就报出错数字 —— 只测默认
排序永远发现不了。凡是「最 X」都写成 `min(列表, key=X)`，凡是计数都不要在刷新
最值时清零。sweep 那一列尤其阴：列头写着「最快」，取的却是最低价那班的时长，
想按「哪天有快班」挑日子的人会被直接带沟里。

**价格历史是分组的，不是一条线。** `floor_history` 以前只按 route + depart 过滤，
于是同一条航线上 JPY 的观测和 CNY 的观测连成一条趋势线，图上出现「一夜跌了
95%」这种纯属换算单位的假信号；商务舱、多人票同理。现在 WHERE 一并卡死币种 /
舱位 / 人数，`trend` 也就有了对应的 `--currency` / `--seat` / `--adults`
—— 它们是「看哪条线」的一部分，不是查询参数。

写入端同样要干净：`record()` 以前记的是**筛过之后**的列表，跑一次
`--airline 春秋` 就往历史里塞一条春秋专属底价；现在记筛之前的全量。
而 `--nonstop` / `--max-stops` 是交给 Google 端筛的，拿回来的压根不是这条航线
的真实底价，这种查询直接不写历史（并在 stderr 说明）。

**发请求之前先把不可能的日期拦掉。** 过去的日期和超出售票窗口（约 11 个月）的
日期，Google 都不渲染结果页，而那种页面跟「这条航线一班都连不上」长得一模一样
—— 每天还要白搭三次重试加退避，最后甩一句吓人的「重试 3 次都没拿到结果列表」，
真实原因只是这天过完了。`sweep` 以前只判断了窗口末尾，窗口开头在过去时那几天
照发请求，还照吃 `--max-queries` 的额度；现在把窗口开头夹到今天并写进「注意」。

**价格一律是「起价」**，不是成交价；输出里每次都写明这一点。

**只查单程，往返靠两次查询拼。** 这是 2026-09-01 用实测数据定下来的：

| 航线 | 往返联程票 | 两张单程 | 差 |
|---|---|---|---|
| 平日 上海↔东京 | ¥2,072 | **¥1,999** | 单程更便宜 4% |
| 平日 上海↔曼谷 | ¥1,460 | ¥1,460 | 完全一样 |
| 平日 北京↔大阪 | ¥2,456 | ¥2,502 | +2% |
| 国庆 上海↔东京 | ¥5,618 | ¥6,074 | +8% |
| 长途 上海↔伦敦 | 查不到 | ¥4,944 | 往返模式更脆 |

往返票几乎没有价格优势，却要付出「每行只是去程航班、价格只是个下限、返程班次
未定」的代价 —— Google 往返查询的第一屏列的就是去程选项，每个挂一句
`From X round trip total`（选这班去程，往返最低 X）。返程班次**抓不到**：
选定去程要用那班的标识符，它不在首屏 HTML 里。

所以脚本**不用 Google 的往返模式**：`tfs` 只拼单程（field 19 恒为 2），
`Itin` 里没有 round_trip，历史库里也没有 ret/one_way 列。
两个确定价格 > 一个下限，而且少一整条代码路径。

`-r/--return` 是**这个决定之上的顺手层**，不是回到往返模式：给了返程日就把
「方向 × 舱位」一次全铺开并发跑，两段各出一张表，开头给出「合计 = 去 + 回」。
合计是两个确定值相加，跟航司卖的往返联程票是两回事 —— 注意栏里写明，别让人
当成往返票价。一段查不到不拖垮另一段：那段位置上印它自己的失败原因和下一步，
另一段照常出表。

加这个参数是因为实测里最常问的就是往返（「中秋回国」「国庆去日本」），而在此
之前想固定日期看往返总价，只能用 `sweep -w 10-05..10-10 --days 5` 逼出唯一
组合这种偏方 —— 能用，但帮助里没写，没人猜得到。

**sweep 因此变成 N+M 而不是 N×M。** 去程和回程各自独立定价，所以扫 N 个出发日
加 M 个返程日就能**算**出全部 N×M 个组合，不必真去查 N×M 次。实测国庆窗口
（9/29~10/8，玩 5-7 天）：原先按组合查 12 次要 5.4 秒，现在 10 次查询 2.85 秒，
组合数一样，而且每段都是确定的航班和价格。

输出刻意分成「去程表 / 回程表 / 最划算的走法」三段而不是一张组合表 ——
去程和回程各自独立可选，糊成一张表反而把「哪天走便宜」和「哪天回便宜」这两个
真正的决策点混在了一起。实测上海↔东京国庆窗口，去程最低 10-03 ¥1,702、
回程最贵 10-07 ¥3,970，这个结构在往返视图里完全看不出来。

### 关键发现六：参数猜错时不给下一步，等于没有提示

脚本里每条 `Failed` 都带「下一步」，唯独 argparse 自己的报错是英文的一句
`unrecognized arguments: ...`，而这恰恰是最常撞上的一类错。现在接管了
`ap.error`：翻成中文，先查一张「打错的写法 → 正解」小表（`ARG_HINTS`），
查不到再用 `difflib` 猜近似参数名（`--nostop` → `--nonstop`）。

`ARG_HINTS` 的键都是**不存在**的参数，会被 `stale_help_flags()` 自动豁免 ——
豁免名单直接从这张表推出来，加新条目不用两处同步。

### 关键发现七：只有一个数据点时，统计摘要全是噪音

`sweep` 的窗口刚好等于天数时只有一种组合，那时「最贵 = 最便宜、贵 ¥0」、
单格走势条自己跟自己比中位数，全是废话。凡是「最值 / 走势 / 中位数」这类摘要，
样本数为 1 时该整段不印，而不是照常渲染出一堆自反的数字。

### 参数分组别把有默认值的写成「必填」

`-d`（默认 14 天后）和 `-w`（默认 14~28 天后）原先都躺在名为「必填：…」的
分组里，跟同组真必填的 `-f`/`-t` 混在一起，也跟「地点必须写明、脚本不猜」
那条设计原则自相矛盾。现在分组叫「航线与日期（出发地、目的地必填）」，
必填的约束回到具体参数的 help 上。

## 维护

历史库改结构时 `reshape()` 会自动重建并搬迁老数据。`CREATE TABLE IF NOT EXISTS`
对已存在的表什么都不做，所以删过列之后老库上**每一次 INSERT 都会抛
IntegrityError** —— 不是历史记不上，是查票整个失败并吐一页 traceback。
开发期去掉 ret/one_way 两列时就是这么炸的，别让用户去自己删库。



`doctor` 有一条**解析器金标准回归**：拿两条实测 `aria-label` 样本（普通中转
和换机场中转各一条）对七个字段。Google 一改句式，抓取会「成功」但字段全空 ——
这是全脚本最脆的一环，靠这条回归让改版立刻报红，而不是等用户拿到空表。

`doctor` 还会对一遍帮助文本里提到的参数是否都真实存在（改参数名忘了改文档）。
